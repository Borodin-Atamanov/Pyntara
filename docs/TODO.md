## Fresh install log findings

Findings from the real fresh-install run captured in gitignore/pyntara_install_real_issues.log (2026-08-26). Each item names the task, the observed line and the place in the code to investigate; reproduce on the target machine and verify the implied goal live.

dnsproxy_setup: DNS bypasses dnsproxy after installation. On the fresh desktop install the active NetworkManager connection keeps static provider DNS on the per-link scope, so the system would bypass dnsproxy. Seen in gitignore/pyntara_install_real_issues.log: 'dnsproxy setup failed: per-link DNS still lists provider resolver(s) 2800:810:100:1:200:115:192:29, 2800:810:100::15, 2800:810:100::9, 810:100::15; the system would bypass dnsproxy'. The task keeps the resolver drop-in and the dnsproxy service and reports a warning, but DNS does not fully go through dnsproxy. The failing check is _verify_system in src/pyntara/tasks/dnsproxy_setup.py, which returns an error when nm_managed and leftover provider addresses remain on a per-link scope. Reproduce on the machine where the install ran, find how the static IPv6 provider DNS ends up in the active connection, and make the task remove static per-link DNS on the connections it manages, or fail the task outright instead of leaving a partial state. The implied goal is that every DNS query on the machine goes through dnsproxy. Хуже всего, что после установки DNS вообще не доступен, ни какой сайт не открывается. Исследовать. Повторить. Спланировать, как исправить.

ca-certificates: 25 trusted certificates were removed during the install. The apt upgrade that three_x_ui_xray_setup triggers updated ca-certificates, and the update removed 25 certificates. Seen in gitignore/pyntara_install_real_issues.log: 'rehash: warning: skipping ca-certificates.crt, it does not contain exactly one certificate or CRL' and '2 added, 25 removed; done.'. Verify on the machine where the install ran whether /etc/ssl/certs now misses certificates and whether HTTPS verification still works; a removal of 25 certificates is abnormal for a plain upgrade and may break TLS trust. Determine whether the engine or the official 3x-ui installer caused it and record the finding; if the engine is the cause, prevent it. Исследовать. Может быть не критично.

three_x_ui_xray_setup: the repository venv python leaks into the official installer. Seen in gitignore/pyntara_install_real_issues.log: '/var/cache/pyntara/repo/.venv/bin/python3: No module named pip' during the installer's fail2ban step. The engine runs under uv run, which prepends .venv/bin to PATH, so python3 inside the official installer resolves to the uv venv python that has no pip. Make _run_installer in src/pyntara/tasks/three_x_ui_xray_setup.py run the external installer with a clean environment, for example a PATH without the repo venv, so it uses the system python3. Reproduce the line first, then confirm the installer no longer sees the venv python.

kde_keyboard_setup: the per-layout hotkey is not applied. The task sets the hotkey, seen in gitignore/pyntara_install_real_issues.log: 'set hotkey Switch keyboard layout to Spanish: Meta+Q', but the kglobalaccel daemon reply after applying is an empty list: '[warn] kde_keyboard_setup: cannot apply hotkey Switch keyboard layout to Spanish: daemon reports []'. The failure is reported at src/pyntara/tasks/kde_keyboard_setup.py line 403. This is an important problem: the keyboard layout switching hotkey is a core part of the KDE setup. Reproduce on a KDE Wayland machine, find why the assignment does not stick (daemon not ready, wrong component_unique, wrong shortcut format), make the hotkey actually apply, and make the task report the applied value instead of an empty list. Критично! Не работает переключение языков после свежей установки! Ни на английски, ни на русский, ни испанский. Исследовать. Решить как исправить.

system_metrics_setup: the deployment venv is not pinned to uv.lock. _ensure_venv in src/pyntara/tasks/system_metrics_setup.py installs pyntara into /usr/local/lib/pyntara/venv with 'uv pip install --python <venv_python> <REPO_ROOT>' and no --locked, so resolved versions drift from the lockfile. Seen in gitignore/pyntara_install_real_issues.log: the repo venv got argon2-cffi-bindings==25.1.0, cffi==2.1.0, pykeepass==4.1.1.post1, while the system venv got argon2-cffi-bindings==26.1.0, cffi==2.1.1, pykeepass==4.2.0 and extra importlib-metadata and zipp. Make the deployment venv install from the lockfile so the deployed services run the same versions as the repository.

inst.sh: the first apt attempt always fails on a fresh system. Seen in gitignore/pyntara_install_real_issues.log: 'E: Package 'python3-venv' has no installation candidate' then 'First install attempt failed, refreshing package index'. The retry after apt-get update works, but on a fresh machine the first attempt is a guaranteed failure and adds about 50 seconds. Consider refreshing the apt index before the first install on a fresh system, or reword the message so an expected retry is not reported as failed. Исследовать. Предложить план исправления на утверждение.
