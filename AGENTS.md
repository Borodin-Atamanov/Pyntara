Система Pyntara. Это система автоматической настройки Kubuntu. Создана для работы на Kubuntu 26.04, однако, спроектирована, чтобы работать и на других версиях.

Система запускается через файл i.sh, и это обычный баш-скрипт. То есть с помощью команды она скачивается с GitHub, сразу запускается под суперпользователем.

Этот bash-скрипт делает некоторые важные проверки, чтобы не сломать систему. Но далее он устанавливает Python, он устанавливает uv и некоторые другие важные необходимые системные утилиты, которые нужны для работы. Такие как wget, curl, nload, htop и множество других. Также он разворачивает Python-систему нужной версии и уже запускает скрипт самой Pyntara.

Затем система спрашивает у пользователя, что, собственно, надо установить. И есть три варианта установки. Минимальная, для сервера или для десктопа. То есть выбирается один, второй или третий вариант. При этом система сама определяет, если это десктоп, то по умолчанию выбран десктоп. И есть отсчёт времени до автоматического выбора. Если ничего не выбрать, то автоматически будет выбран нужный вариант. На десктопе запустится десктоп, на сервере запустится серверный вариант. Время на выбор 11 секунд. И оно тикает на экране, то есть видно, как уменьшается количество времени, если не двинуть клавишами вверх, вниз, вправо-влево или Enter. Затем появляется в терминале выбор с помощью чекбоксов тех задач, которые выполняет Pyntara. Это задачи по настройке системы. У задачи есть заранее заданная очередность, есть название задачи и есть описание задачи, что там происходит внутри человеческим языком. Все эти задачи задаются в конфигурации.

Нужно выбрать лучшую архитектуру загрузки всего репозитория из GitHub. Может быть, это какие-то релиз-файлы, или может быть это один большой файл, который содержит всю информацию. Какой-то вариант, который был бы наиболее прост для скачивания даже с плохим и нестабильным интернетом. Потому что гит иногда может отваливаться. Но гит как вариант по умолчанию вполне подходит.

В репозитории Pyntara'ы есть файл с секретами в формате KeePass. Одна из программ, которая устанавливается на этапе первоначальной загрузки, это консольный клиент для base KeePass. После того, как выбраны галочками отмеченные чекбоксами задачи, которые будут выполняться, происходит запрос пароля у администратора, настраивающего компьютер, с помощью Pyntara. И этот пароль используется для расшифровки базы паролей. Если пароль неверный, то у пользователя спрашивают, нужно ли использовать секреты по умолчанию. Секреты по умолчанию хранятся в GitHub в открытом виде, потому что они не секретные, самые обычные. Там нет секретной информации. А если введен правильный пароль, то происходит расшифровка базы паролей, и из этой базы паролей некоторые секреты превращаются в переменные окружения. Некоторые из них затем будут сохранены во внутренней конфигурации компьютера. А некоторые используются только один раз, и они находятся только в оперативной памяти компьютера в момент запуска Pyntara.

Таски, задачи, которые выбираются с помощью чекбоксов, на самом деле имеют не два состояния, а как минимум три. Дело в том, что каждая задача должна использовать принцип идемпотентности, то есть выполнение задачи не должно разрушать уже настроенную систему. Например, если уже установлена какая-то программа, то устанавливать ее заново не требуется. Однако, если заново запустить команду на установку программы, то затирания не произойдет. Однако, есть другие задачи, которые, например, редактируют системные файлы, что-то туда записывают или удаляют, или меняют, или скачивают новый профиль для браузера, или делают что-то еще, например, генерируют новый пароль для root. В этом случае каждая задача должна использовать принцип идемпотентности, то есть не перезаписывать по умолчанию уже записанные данные. Однако, у каждой задачи есть режим force, когда задача выполняется, даже если она уже была выполнена ранее.

В файле конфигурации записано про каждую задачу, task, что она делает, каким файлом она запускается. Вероятно, разумно сделать, что каждая задача – это отдельный файл в отдельной директории задач. Также у задач могут быть дополнительные данные. В частности, например, задача по установке и настройке ssh сервера. Она устанавливает ssh сервер, перенастраивает конфигурацию SSH демона и добавляет, куда следует, заранее сгенерированные сертификаты, чтобы на настроенную машину можно было зайти по сертификату без использования пароля.

У файла задачи всегда то же имя, что и задано в конфигурации задач. Данные по задаче хранятся в папке данных всех задач. Папка с данными задачами называется точно так же, как задача.

У задач может быть своя конфигурация, которая тоже сохраняется в папке с данными задачи.

Есть задача по установке телеметрии в системе. Самая главная телеметрия, которая устанавливается, это при старте системы происходит проверка на доступ к сети. Если доступа к сети нет, то увеличиваются интервалы ожидания. Каждый раз на 40% больше, в корень из двух раз больше времени. Сначала одна секунда, потом 1,4 и так далее. Если появилась сеть, то телеметрия пытается отправить данные, куда следует. В секретах есть адрес телеграм-бота, куда надо отправлять сообщения и файлы, а также есть Google Drive, куда нужно загружать файлы телеметрии. Телеметрия создается с помощью зашифрованных PDF-файлов. Шифрация с помощью AES-256 алгоритма строго. Самая мощная, которая есть. Пароль, с помощью которого происходит шифрование этих PDF-файлов, генерируется при инициации Pyntara. Этот пароль для шифрования генерируется на основании соли, которая задана в базе секретов KeePass, которая расшифровывается с помощью пароля, который вводит администратор, и с помощью имени хоста. Имя хоста определяется, генерируется случайно, 9 символов случайных, генерируется при как одна из выполняемых задач.

При создании любых документов с кодом, конфигурационных файлов и так далее, создаются комментарии на простом английском языке, объясняющие, что делает код, что выполняет каждая строчка в конфигурации, зачем делается то или иное действие, почему выбрана та или иная архитектура. Всё должно быть объяснено достаточно подробно, чтобы человек или машина, читающие код, легко могли его понять. Строго соблюдаются стандарты форматирования и стиля кода, единые для всего проекта.

Одна из задач – это настройка для этой машины индивидуального NextDNS аккаунта. Для этого через браузер в режиме автоматизации заходится на сайт, создается новый аккаунт, и этот аккаунт выдает конкретный уникальный адрес для DNS-запросов. Этот адрес для DNS-запросов прописывается в систему таким образом, чтобы все запросы от этого компьютера шли только через эти DNS-сервера. Естественно, что созданный адрес записывается в телеметрию, и сам сервис NextDNS сохраняет все запросы с возможностью настройки фильтрации.

Поправить конфиг и изменить в нем только те строчки, которые нужно изменить, а все остальное вообще не трогать в независимости от того, что там есть оставить все комментарии, оставить все, что есть для этого используется. Телеметрия копится один день. Если был успешный факт отправки, то следующая отправка происходит в 12 часов дня по местному времени. Однако, если есть неотправленные телеметрии файлы, то попытки отправки происходят постоянно, пока не увенчаются успехом, с интервалами времени, увеличивающимися в корень из двух раз. У телеметрии есть две независимых очереди отправки сообщений. Архитектурно сделано так, что могут добавляться и другие независимые очереди. Одна очередь – это отправка через Telegram, а вторая очередь – это отправка через Google Drive, Google Docs. И в том, и в другом случае отправляются зашифрованные PDF-файлы. Причем сами PDF-файлы создаются в памяти так, чтобы на диске не хранились незашифрованные версии этих файлов. После отправки файлы телеметрии сохраняются в специальной папке.

Кроме того, телеметрия сохраняет скопированный в буфер обмена текст. И точно так же, как и DNS-данные, точно так же, как и другие данные, отправляет в виде зашифрованных PDF-файлов.

При старте компьютера происходит попытка определения всех сетевых адресов, подключения к Cloudflare, Yggdrasil, IPv6 и другим сетевым каналам. Определяются собственные адреса компьютера, и они отправляются в телеметрию в виде зашифрованных файлов. Информация о том, что компьютер включен, и как к нему можно подключиться.

Есть задача по установке и настройке ZRAM. И отдельная задача, task, по настройке и созданию SWAP файла. ZRAM автоматически настраивается в зависимости от количества ядер процессора. Если по какой-то причине их определить не удалось, то ставится равным восьми. ZRAM ставится агрессивный, с хорошим сжатием и на практически весь размер памяти. То есть вся память становится сжатой. Отдельный task по созданию файла подкачки. В конфигурации этих task'ов есть формулы, которые задают, какой размер файла подкачки используется, создается в зависимости от того, какой есть размер оперативной памяти и от количества свободного места на жестком диске.

Таск один из – это создание прокси-сервера на компьютере с паролем, авторизация на порту. Это позволяет через любые открытые сетевые соединения использовать этот компьютер как прокси-сервер. Также этот прокси-сервер настроен как системный сервис, который управляется стандартными средствами Kubuntu, как и другие сервисы, которые работают в фоне и настраиваются с помощью системы Pyntara.

Pyntara создает сервисы. Эти сервисы пишут логи, куда им положено писать по Linux-стандартам. Естественно, логи с ротацией. Кроме того, установочный лог, то есть лог того, как Pyntara устанавливалась на систему, все подробные сообщения, которые в этот момент выводились, все это отправляется в телеметрию отдельным файлом. Другие логи не отправляются в телеметрию на регулярной основе, остаются на компьютере с включенной ротацией логов. То есть, конечно, логи не должны занимать все свободное место. Логи, которые создает каждый сервис Pyntara, по умолчанию достаточно подробные. При этом есть уровни подробности, и по умолчанию все сервисы Pyntara подробно описывают все действия, которые они выполняют в системе. Последовательно рассказывают историю, что произошло, что вернула какая команда и так далее. Но в логи не должны попадать секреты. Секреты в логах скрываются и не попадают в открытом виде.

Отдельный таск – это настройка локального прокси-сервера на компьютере. Поднимается соединение к удаленному прокси-серверу. Данные для соединения берутся из файла с секретами, которому администратор в явном виде вручную вводит пароль при запуске системы Pyntara. И оттуда берется способ подключения, адрес подключения точнее, и происходит подключение к удаленному прокси-VPN-серверу и создание локального порта, к которому могут подключаться любые приложения.

Pyntara помогает сохранить настройки браузеров. Для этого в проекте Pyntara есть способы запуска Firefox, Chrome и Chromium с отдельным профилем. Затем специальный скрипт, возможно, через Prompt с подключением и агента на локальной машине, например, агента Гермес, создает специальный JSON-файл, который позволяет через корпоративные варианты настройки браузера добиться того, чтобы браузер установил нужные расширения, чтобы были скопированы все настройки для этих расширений и настройки для самих браузеров. Кроме того, по умолчанию в системе браузеры запускаются таким образом, чтобы ими могли управлять интеллектуальные агенты через разные интерфейсы, позволяющие такое управление. То есть, чтобы агенты могли управлять именно тем окном браузера, которое уже открыто, а не открывать другое окно в фоне, невидимое для пользователя компьютера. Модель передачи данных между компонентами. Использование глобальных переменных модуля запрещено для любых данных, которые представляют состояние приложения — конфигурация, учётные данные, результаты выполнения задач. Единственная точка сборки состояния — точка входа программы, так называемый composition root, реализованная как обработчик команды CLI на typer. Здесь и только здесь загружается конфигурация из файла, переменных окружения и флагов командной строки, приводится к одному объекту через модель pydantic, с приоритетом: флаг командной строки перекрывает переменную окружения, переменная окружения перекрывает значение из файла, файл перекрывает встроенное значение по умолчанию. Результат сборки — один неизменяемый объект, называемый RunContext, содержащий разрешённую конфигурацию, экземпляр хранилища секретов и другие сквозные зависимости. RunContext передаётся вниз по всем вызовам как явный параметр функции; ни одна функция не должна читать состояние приложения из os.environ (кроме тех, которые для этого спроектированы), из module-level переменной или из любого другого неявного источника, если это состояние не было явно передано ей аргументом.

Каждая задача настройки системы реализуется как функция, принимающая RunContext и, при необходимости, собственные типизированные параметры, и возвращающая объект TaskResult — dataclass с полями об успешности выполнения, произведённых изменениях и тексте ошибки при её наличии. Если одной задаче нужен результат другой задачи, передача происходит одним из двух явных способов: либо через метод доступа у объекта, находящегося в RunContext, например у хранилища секретов, либо оркестратор задач явно берёт TaskResult предыдущей задачи и передаёт нужное значение аргументом следующей. Скрытая передача данных между задачами через любую разделяемую изменяемую переменную вне RunContext и вне явных аргументов запрещена.

Для описания контракта "что такое задача" использовать typing.Protocol — структурную типизацию по сигнатуре вызываемого объекта — вместо абстрактного базового класса с обязательным наследованием. Классы с внутренним состоянием и поведением допустимы только там, где нужна инкапсуляция — например клиент доставки телеметрии — и такие классы должны создаваться один раз в точке входа и передаваться через RunContext, а не инстанцироваться заново внутри задач; это требование dependency injection: зависимость передаётся объекту снаружи, а не создаётся им самим.

Логирование через стандартную библиотеку logging с получением логгера по имени модуля и передачей записей через SysLogHandler в системный журнал является допустимым исключением из запрета на общее состояние, поскольку logging не несёт бизнес-логики и спроектирован для сквозного использования.

Единственная законная форма общего состояния вне памяти одного процесса — это данные на диске или в межпроцессных каналах: файл зашифрованного хранилища секретов, очередь телеметрии в виде файлов в отдельной директории, именованные каналы для межпроцессных команд. Эта граница между процессами, обслуживаемыми разными systemd-сервисами, должна быть явно описана в файле описания архитектуры как осознанный контракт коммуникации, а не смешиваться с внутрипроцессными глобальными переменными Python, которые в этом проекте не допускаются ни в каком виде.

Стандарты кода. Все функции и методы обязаны иметь полную аннотацию типов для всех аргументов и возвращаемого значения без исключений. Соответствие типов проверяется библиотекой mypy в строгом режиме; сборка не считается прошедшей проверку при наличии хотя бы одной ошибки типов. Форматирование и статический анализ кода на предмет неиспользуемых переменных, опасных конструкций и нарушений стиля выполняется библиотекой ruff; код обязан проходить проверку ruff без предупреждений перед слиянием любого pull request. Вызовы внешних команд через subprocess обязаны производиться без параметра shell=True и с обязательной проверкой кода возврата. Каждая операция настройки системы обязана быть идемпотентной: перед внесением изменения задача проверяет текущее состояние системы и пропускает изменение, если система уже находится в целевом состоянии; повторный запуск программы не должен приводить к порче уже настроенной системы и не должен перезаписывать уже сгенерированные секреты. Хранение секретов в открытом виде где-либо, включая логи и код, запрещено;. Модель данных и валидация внешних входных данных, включая конфигурационные файлы, выполняется через pydantic; структуры результатов и внутренние данные без необходимости валидации оформляются как dataclass.

Тестирование. Каждый модуль с логикой задачи обязан сопровождаться модульными тестами на pytest в той же директории tests, в том же pull request, в котором эта логика вводится. Все обращения к внешним системным ресурсам — subprocess, файловая система, сеть — в модульных тестах обязаны подменяться через monkeypatch, чтобы тест не производил реальных изменений на машине, где он выполняется. Для проверки логики, работающей с файлами, использовать встроенную фикстуру pytest tmp_path, которая предоставляет временную директорию, автоматически удаляемую после теста, вместо обращения к реальным путям файловой системы. Для каждой задачи обязателен как минимум один тест, проверяющий успешный путь выполнения, и как минимум один тест, проверяющий поведение при ошибке — например, при недоступности внешней команды или при отсутствии прав доступа. Тесты хранилища секретов обязаны проверять, что при повторной загрузке уже созданного хранилища возвращаются те же значения, а не генерируются новые. Прохождение ruff, mypy в строгом режиме и полного набора pytest обязано быть настроено - не допускается загрузка в репозитарий без этих проверок.
